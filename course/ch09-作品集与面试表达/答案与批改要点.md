# 第 9 章 · 答案与批改要点

> 本章没有标准答案，但有**明确的评分标尺**。
> 下面给一份完整的范例（用第 4 章的日报管道），你可以照着改。

## 任务 1｜一页纸作品集（范例）

```markdown
# 多站点日报管道

## 1. 一句话
给跨境电商运营团队做的日报自动化管道：把 8 个站点的日报汇总从
55 分钟/天降到 5 分钟/天，并自动指出数据异常。

## 2. 问题与背景
- 运营专员每天 9:00–10:30 手工登录 8 个站点后台，下载 16 个 CSV，
  粘贴进 Excel 模板算 ACOS 与退款率，单次 90 分钟、每周 5 次。
- 上月因漏掉美国站，一个高 ACOS 广告组连续 3 天无人处理，损失约 800 美元。
- 业务现状：4 人围观、1 人操作，早会要用昨天的数，实际只能拿到前天的。

## 3. 方案与架构
```
报表 CSV ──► 清洗(时区/去重/取消单) ──► 宽表(日×ASIN)
                                          │
广告报表 ─────────────────────────────────┤
结算单 ──► 订单级费用回填下单日 ──────────┤
                                          ▼
                                   对账桥 + 异常清单
                                          │
                                   日报 Markdown/CSV + 告警
```
三句话：① 业务报告打底保证行集完整；② 广告先聚合再连接、父体摊到子体；
③ 费用按下单日归集，否则跨月丢失。

## 4. 关键取舍
- **不用 Agent**：这是一条固定流水线，Agent 的多步决策只会增加不确定性和成本；
  早会用数，**错了比慢了严重**。
- **不用 pandas**：公司电脑装不了包，纯标准库（csv/logging/dataclasses）零依赖，
  任何一台机器 `python run.py` 就能跑。
- **不做网页 UI**：先用 Markdown + 定时推送覆盖 90% 场景，做 Web 要两周，
  而业务只要"早上看到数"。

## 5. 结果
| 指标 | 上线前 | 上线后 |
|---|---|---|
| 单次汇总耗时 | 90 分钟（基线：让小李记 3 天工时） | 5 分钟（含人工核对） |
| 漏站次数 | 1 次/月 | 0（缺失即告警） |
| 数据一致性 | 手工错误率约 8% | 对账残差 0.00 |

上线 3 周累计 42 次运行，节省约 34 小时；单次成本 0.0013 元。

## 6. 我的贡献
独立完成：需求访谈、口径对齐、全部代码（约 800 行）、部署与健康检查。

## 7. 已知不足与下一步
- 单日运行不做对账（结算单是滚动账本，短区间必然不平）→ 目前对账单独按月跑。
- 只支持 US 站；配置里预留了站点维度但未验证第二站点。
- 金额用 float，长期应收敛为整数分。
- 下一步：加"异常项一键确认"埋点，用来衡量工具是否真的进入工作流。

## 8. 链接
仓库：…（含 9 个测试）；演示录屏：…；数据字典：…
```

### 评分标准

| 项 | 满分 | 常见扣分 |
|---|---|---|
| 一句话讲清价值 | 2 | 写成了技术描述 |
| 背景有数字 | 2 | 只有形容词 |
| 架构能看懂 | 2 | 只有代码没有图 |
| 取舍 ≥2 条且有判据 | 3 | 只写"我选了 A"，没写为什么不用 B |
| 结果有基线来源 | 3 | "提升 80%" 但说不出从多少到多少 |
| 贡献边界清楚 | 2 | "我们团队做的" |
| 不足是真的 | 2 | 写成"暂时没发现问题" |

## 任务 2｜讲述稿骨架（"取舍"那段写满）

**① 背景（2 min）**

> "我先说背景。运营每天早上要用昨天的数据开早会，但实际情况是：
> 一个人要手工登 8 个站点、下 16 张表、拼到一个 Excel 里，90 分钟。
> 结果早会开的时候拿的是前天的数。更严重的是上个月漏了一个站，
> 一个广告组失控了 3 天，损失 800 多美元。"

**④ 取舍（4 min，这段最值钱）**

> "做这件事有三条路。第一条是规则脚本，第二条是让模型写 SQL 再执行，
> 第三条是做个 Agent 每天自己跑。我选第一条，理由有三个：
>
> 第一，**规则能写下来**。汇总、算 ACOS、对账，全是确定性逻辑。
> 让模型参与只会引入不确定性——同一个输入今天算 100，明天算 100.5，
> 这在财务场景是不可接受的。
>
> 第二，**成本结构不同**。脚本每天跑一次几乎不花钱；模型每天跑 8 次，
> 一年几百块，但更贵的是**排查成本**：模型算错了，你要去查 prompt、查温度、
> 查上下文，而脚本错了看一行日志就够。
>
> 第三，**后果不对称**。这份数据要在早会上拍板，错了比慢了一个小时严重得多。
> 所以任何"可能自己发挥"的方案，我都不考虑。
>
> 我确实考虑过 Agent，因为它能自动处理站点改版。但权衡下来，
> 站点改版一年一两次，我加一次配置就够；而 Agent 的不确定性是每天都有的。
> **用每天的不确定性，换一年两次的便利，不划算。**"

**⑤ 结果（3 min）**

> "上线 3 周跑了 42 次，成功率 100%。耗时从 90 分钟到 5 分钟，
> 其中 5 分钟里 4 分钟是人工核对——我故意保留这一步，因为**人需要一次确认才敢用**。
>
> 这里我要说清楚：基线 90 分钟不是用户随口说的，
> 是让小李记了 3 天实际耗时，平均 88 分钟。
>
> 但我要强调：**我证明的是过程指标（省了时间），不是业务结果**。
> 业务结果我只观察到一个案例：11 月 12 日工具标出某个品库存只剩 3.6 天，
> 当天补货，避免了断货。这个案例值多少钱，我没法精确归因。"

**⑥ 复盘（2 min）**

> "如果重做，我会改两点：一是**先做一周的手工并行对比再写代码**，
> 我一开始直接写，结果口径对了三次才对齐；二是**提前设计埋点**，
> 现在我只能证明'跑了 42 次'，证明不了'业务真的每天在看'。"

## 任务 3｜30 题答题要点（速查）

| # | 题 | 一句话要点 |
|---|---|---|
| 1 | 需求谁提的 | 主管提的，但我下去跟操作的人聊了 40 分钟，发现真实痛点在"漏站"而不是"慢" |
| 2 | 用户只要按钮 | 先问"按钮点完之后你拿它做什么"，往往能发现更深的需求；实在不需要就说明利害关系 |
| 3 | 做过没人用的东西 | 诚实举一个，给原因（数据不可信/多了一步），给后来的改进 |
| 4 | 怎么排优先级 | RICE + 数据可得性；数据拿不到的直接降级 |
| 5 | 怎么证明省时间 | 让用户记 3 天工时，取平均；不用"我觉得要一个多小时" |
| 6 | 停了会怎样 | 说清谁会用不了（4 个人的早会），这是价值的反向证明 |
| 7 | 时区 | 落库统一 UTC，派生业务日期按站点时区；ERP 北京时间减 16 小时 |
| 8 | 数不一样 | 先讲五层口径（GMV→净销售→结算净额→毛利），再展示对账桥 |
| 9 | 脏数据 | 去重按业务主键、空值不硬改只打标、0 分母返回 None、异常进清单 |
| 10 | 重跑一致 | 产物不含时间戳、显式排序、原子写；实测 md5 相同 |
| 11 | 退款口径 | 业务报告按下单日，结算按退款发生日；对账时把差额作为"时点差"加回 |
| 12 | 上游改格式 | schema 校验（必需列），缺列直接抛错并告警，不静默 |
| 13 | 为什么不用 SaaS | 数据合规/成本/集成/可控性四维；内部工具数据不出内网 |
| 14 | 为什么 TF-IDF | 几百 chunk 场景够用且可解释；上万条或同义多再上 embedding |
| 15 | prompt 管理 | 独立文件 + 版本号 + 评估集回归，改完跑分再上 |
| 16 | 输出不合法 | 解析容错三层 + schema 校验 + 带错误信息重试 3 次 + 落 failed.jsonl |
| 17 | 控成本 | 预算上限 + 缓存 + 模型分级 + 熔断 |
| 18 | 为什么不用 Agent | 确定性任务用不上；Agent 的成本和不确定性是负债 |
| 19 | 挂了怎么恢复 | runbook + 回滚脚本 + tag；演练过，5 分钟内恢复 |
| 20 | 怎么测不确定系统 | mock 双模式 + 规则判定（格式合规）+ 人工抽检（质量） |
| 21 | 怎么让业务用 | 种子用户参与设计 → 并行一周 → 15 分钟培训 → 示范案例 → 写进 SOP |
| 22 | 有人抵触 | 先找愿意的人做出案例，用案例说服；不硬推 |
| 23 | 怎么做培训 | 15 分钟，只讲何时用、三步操作、出问题找谁 |
| 24 | 怎么知道变差了 | 埋点（成功率/耗时/失败原因）+ 每周看 Top3 |
| 25 | 跟非技术同事沟通 | 不问"要什么功能"，问"现在怎么做、上次花多久" |
| 26 | 失败的项目 | 用 STAR，重点是自己哪一步判断错了 |
| 27 | 有争议的决策 | 例如"不做网页 UI"，理由是覆盖 90% 场景、成本差 10 倍 |
| 28 | 重做会改什么 | 至少 2 点，且是真的（先并行验证、先埋点） |
| 29 | 什么情况下崩 | 上游报表改版 + 机器关机 + 数据源权限被收回 |
| 30 | 怎么判断止损 | 留存连续 3 周 <30%、失败原因不是你能修的、维护成本 > 收益 |

## 那张"最狠的一问"怎么答

> **"你说省了 34 小时。这 34 小时，公司真的省到钱了吗？"**

**不及格**：能啊，34 小时 × 90 元 = 3,060 元。

**及格**：
> "严格说不能直接换算。省下来的时间如果只是让人早下班，公司没有多赚一分钱。
> 我能证明的是三件事：一是这 34 小时被重新投入到了广告结构优化上，
> 试点一个月 ACOS 从 26% 降到 19%；二是漏站率从每月 1 次降到 0，
> 按历史事故 800 美元/次估算，年化约 1 万美元；三是手工错误率从 8% 降到 0。
> **第一条是推理，后两条有数据。**"

**优秀**（在上面基础上加）：
> "所以我建议上线后按三项分开计量：节省工时、避损、广告费率变化。
> 混在一起算一个'总收益'，反而会让老板觉得你在凑数。"

## 我会追问穿的三处（提前准备）

1. **"你说的省时间，谁测的？"** → 答不出基线来源就废
2. **"为什么不用 XX？"**（你方案里任意一个技术点）→ 答"够用了"要配判据
3. **"如果数据拿不到呢？"** → 看你有没有 B 计划（砍输入 / 手工导入版）
