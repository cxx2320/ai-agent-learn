# 附录 A · 技术预研：怎么验证一个新能力值不值得用

> JD 职责五原话："关注 AI 工具与应用的发展，**验证适合公司业务的新能力**，沉淀项目经验、应用案例及可复用组件。"
>
> 前面九章教你"怎么做东西"，这一篇教你"**怎么判断一个新东西值不值得做**"。
> 这是唯一一项"不产出代码也要产出结论"的能力，也是最容易被面试官问到的。

---

## A.1 为什么预研是独立技能

新手做预研的典型过程：

> 看到一个新模型/新工具 → 觉得很强 → 花两天搭个 demo → 效果惊艳 → 写报告推荐 → 上线 → 踩坑

问题不在 demo，在于**你验证的是"能不能"而不是"值不值得"**。

合格的预研回答四个问题：

```
① 它能不能做到（能力上限）
② 做到要多少钱、多快（成本与延迟）
③ 出错时会不会把事情搞砸（稳定性与失败模式）
④ 换掉它有多难（退出成本）
```

**只验证 ① 的预研，等于没做。**

## A.2 半天法则（Time-boxed Spike）

**限时 4 小时，到点必须给结论**，哪怕结论是"暂不采用"。

| 时段 | 做什么 | 产出 |
|---|---|---|
| 0:00–0:30 | 定义**一个**具体任务 + 一条验收线 | 一句话任务 + 数字标准 |
| 0:30–1:30 | 跑通最小闭环（能出结果就行） | 一份可复现的命令 |
| 1:30–3:00 | 用**你的黄金集**跑 20 条 | 通过率、成本、耗时 |
| 3:00–3:30 | 故意让它失败（坏输入/边界） | 失败模式清单 |
| 3:30–4:00 | 写一页结论 | 采用 / 观望 / 不采用 + 理由 |

**为什么必须限时**：预研最大的风险不是结论错，是**无限期地"再看两天"**。
一个新模型过两个月就过时了，你追不上。

## A.3 五维评估表（打勾用）

| 维度 | 要问的问题 | 不合格的信号 |
|---|---|---|
| **能力** | 在我的黄金集上通过率多少？ | 只在官方 demo 上好看 |
| **成本** | 单次多少钱？月成本多少？ | 算不出"每次调用"的单价 |
| **延迟** | 用户等待多久？批量跑多久？ | 单条 30 秒以上还串行 |
| **稳定性** | 失败率？失败可恢复吗？ | 失败没有错误码，只有"出错了" |
| **合规与集成** | 数据出不出内网？能不能接现有系统？ | 必须上传客户数据到第三方 |

### 每一维的及格线（跨境场景）

| 维度 | 及格 | 备注 |
|---|---|---|
| 能力 | 黄金集 ≥ 80%，且**错的部分不致命** | 政策/财务类要 ≥ 95% 或加人审 |
| 成本 | 月成本 < 省下的人力成本 1/5 | 留出 5 倍余量给增长 |
| 延迟 | 单条 < 10s，批量 < 30min | 早会前要出结果 |
| 稳定性 | 成功率 ≥ 98%，失败可重试 | 否则不敢无人值守 |
| 合规 | 数据不出内网，或不含个人信息 | 客户数据出境是红线 |

## A.4 一页纸预研报告（模板）

```markdown
# 预研：<能力/工具名>   日期：____   负责人：____

## 结论（先写这个）
采用 / 观望 / 不采用 —— 一句话理由。

## 任务定义
在 <场景> 上，用 <输入> 产出 <输出>，验收线是 <数字>。

## 实测数据
| 指标 | 结果 | 及格线 |
|---|---|---|
| 黄金集通过率 | | ≥80% |
| 单次成本 | | |
| 单条延迟 | | <10s |
| 失败率 | | <2% |

## 失败模式（最重要的部分）
1. 在 <什么输入> 下会 <怎么错>，后果是 <什么>
2. ……

## 成本测算
单次 ___ 元 × 每天 ___ 次 × 30 = ___ 元/月

## 集成与合规
- 数据流向：
- 需要哪些权限：
- 退出成本：换掉它要改 ___ 处

## 建议
下一步：<最小可行动作>，预计 ___ 天，需要 ___ 支持。
```

**注意"结论"写在最前面**。领导只看得完第一段。

## A.5 三个 Playbook

### Playbook 1：评估一个新模型能不能替换现有模型

```
① 拿你现有的黄金集（第 5 章那 20 条）原样跑一遍，不改 prompt
② 对比：通过率 / 单条成本 / 延迟 / 失败模式差异
③ 只在"通过率不降"且"成本或延迟明显更好"时才考虑换
④ 换之前：把新旧模型的输出各存 50 条，做盲评
```

**关键**：**不改 prompt 直接跑**。改了 prompt 再比，你测的是"你的调参能力"，不是模型。

### Playbook 2：评估一个 SaaS 工具该不该买

按顺序问五个问题，任一答"不行"就停：

1. 数据要不要出内网？（要 → 基本否决，除非是脱敏后的聚合数据）
2. 能不能导出原始数据？（不能 → 你被锁定）
3. 单账号多少钱 × 几个人？（先算年费）
4. 有没有 API？（没有 → 只能人工点，等于没集成）
5. 换掉它要多久？（迁移成本 > 一年省下的时间 → 不买）

### Playbook 3：评估一个新框架/库

```
① 能不能在现有环境装上（Python 版本、依赖冲突、需不需要 C 编译）
② 团队里除了你还有谁会？（只有你会 → 你走了就是债）
③ 出问题有没有社区/文档？（小众库 = 自己读源码）
④ 退出成本：它是只在一个模块里，还是会污染全局？
```

**经验值**：内部小工具，**能不引入依赖就不引入**（这也是本课程全程用标准库的原因）。

## A.6 Demo 效果好 ≠ 生产能用（三个幻觉）

| 幻觉 | 真相 | 怎么破 |
|---|---|---|
| "demo 里效果很好" | demo 是你挑过的 3 个样例 | 用没挑过的 20 条跑 |
| "官方说准确率 95%" | 那是他们的评测集，不是你的业务 | 用自己的黄金集 |
| "跑得挺快的" | 你只跑了 5 条 | 跑 200 条看 P95 延迟 |

还有一个最隐蔽的：

> **"我试了 20 次都成功了"** —— 20 次全成功，在 98% 成功率下概率是 67%，
> 什么都证明不了。**要证明稳定性，你得跑够样本量，或者看失败长什么样。**

## A.7 沉淀：预研的真正产出不是结论，是资产

每次预研结束，至少留下三样东西：

1. **一页报告**（进内部 wiki，标日期和版本）
2. **可复现的脚本**（下次别人不用从零开始）
3. **失败的记录**（"我们试过 X，因为 Y 不适合"——这条比正面结论更值钱）

> 岗位 JD 说"沉淀项目经验、应用案例及**可复用组件**"。
> 这个仓库里的 `course/templates/`、`check_course.py`、`ops/healthcheck.py` 就是这类沉淀物。

## A.8 过关标准

- [ ] 能用半天法则完成一次预研（限时 4 小时，到点出结论）
- [ ] 报告里"失败模式"不是空的，且写了后果
- [ ] 能算出单次成本与月成本
- [ ] 能说出"退出成本"（换掉它要改几处）
- [ ] 能识别"demo 幻觉"的三种表现
- [ ] 每次预研都留下脚本，别人能复现

## A.9 一个练习（1 小时）

选一个你最近听到的新模型/新工具，按 A.2 做一次 4 小时限时预研，
用 A.4 的模板写一页报告（**结论写在最前面**）。

如果你手上没有现成的黄金集，就用第 5 章的 8 个产品 + 7 条校验规则
（`ch05/solution/tests/test_listing.py` 里的规则）当作简易评估集。
