## 任务 1｜各模块关键实现

### `schema.validate_listing`

```python
if not 60 <= len(title) <= 180:            failed.append(RULE_TITLE_LEN)
if has_chinese(title):                     failed.append(RULE_TITLE_EN)
if len(bullets) != 5:                      failed.append(RULE_BULLETS_5)
elif not all(120 <= len(b) <= 300 ...):    failed.append(RULE_BULLET_LEN)   # ★ elif
```

三个细节：
1. **`elif` 而不是 `if`**：条数不对时不要再报长度错，否则一次报两个错，模型会懵
2. 关键词命中要 `title.lower()`（大小写不敏感）
3. 禁用词查 `title + bullets` 的**拼接文本**，不区分大小写

### `schema.parse_json`

四层兜底，`solution` 里的顺序：

```python
candidates = [raw]                     # 1) 直接解析
m = _FENCE.search(raw)                 # 2) 剥 ```json 代码块
lo, hi = raw.find("{"), raw.rfind("}") # 3) 截取 {...}
```

**先剥代码块再截取**，顺序不能反：先截取会把 ```json 那行也带进 JSON 字符串里。

### `llm.mock_complete`（本任务最容易翻车的地方）

必须同时满足：

| 约束 | 做法 |
|---|---|
| 标题 60–180 | 先拼，短了补 `" with Premium Build"`，长了按 177 截断 |
| 关键词 ≥2 | **把关键词放在标题最前面**，这样截断也不会丢 |
| 每条 120–300 | `while len(text) < 120: text += "..."`，再按 296 截断 |
| 全英文 | 只从 `卖点` / `目标关键词` 两行取词（这两行是英文），**绝不碰 `名称`** |
| 无禁用词 | 生成文本的用词表里不能有 best/sale 等 |

> 特别注意"截断"：如果你把关键词放在标题**末尾**，截断时会把 `desk charger` 切掉，
> `含 ≥2 个目标关键词` 这条就挂了。**顺序也是正确性的一部分。**

### `evaluate.summarize`

空输入返回全 0（`if total == 0: return {...}`），否则 `summarize([])` 会 ZeroDivisionError。
这个防御不是洁癖——`--resume` 二次运行时，本次新处理 0 条是很正常的状态。

## 任务 2｜报告解读的参考答案

1. **通过率 100%、平均得分 100%** —— 这是**预期结果**，因为 mock 是按规则倒推生成的。
2. **失败分布为空** —— 正好说明报告没在骗人：mock 不会失败，失败的是真模型。
3. **总成本 0.006235 元**（8 条，约每条 0.00078 元）。**mock 也算钱**，这是刻意设计：
   如果你把成本统计写在 `if not mock` 分支里，就永远测不到成本逻辑。
4. **重试率 0%** —— 正常。但重试率**长期为 0** 反而要警惕：说明校验可能太松，
   或者你根本没在看这个指标。

**加分观察**：报告开头必须有"本报告来自 mock，不能证明文案质量"的警告。
拿 mock 的 100% 去汇报，是新手最典型的自欺欺人。

## 任务 3｜Prompt 迭代实验

**3.4 的标准答案**：

> 只改 prompt 不改校验 → **校验还在用旧标准**，于是：
> 模型按 80–150 写，校验按 60–180 判，两者都不报错，**你以为改生效了，其实没有约束力**；
> 或者相反，模型按旧的写、校验按新的判，通过率暴跌但原因不明。
>
> 更严重的是**prompt 与校验漂移**：三个月后没人知道哪条规则才是真的。

**工程化解法**（能答出这个分就很高）：

```yaml
# config/listing.yaml
title_min: 80
title_max: 150
```

prompt 模板用 `{title_min}` / `{title_max}` 占位，校验用 `cfg.title_min`。
**同源，改一处两处一起变。**

## 任务 4｜依赖注入与重试

改造签名：

```python
def generate_one(..., completer=None):
    completer = completer or llm.complete
```

三个测试（实测已通过）：

| 场景 | 断言 |
|---|---|
| 第一次就成功 | `attempts == 1`、`ok is True` |
| 第二次成功 | `attempts == 2`、`ok is True` |
| 三次失败 | `attempts == 3`、`ok is False`、`failed` 非空 |

**4.3 的回答**：

> `failed.jsonl` 三个月后是**唯一的现场证据**。
> 只写 `"failed"` 你只知道"挂了"；写上 `["标题 60-180 字符"]` 和最后一次的原始输出，
> 你才知道"模型总是写到 190 字符"→ 去改 prompt 或放宽上限。
>
> **失败日志的价值 = 它能直接指向你要改的那一行。**

**重试的两个反直觉细节**：
1. 第二次起 `temperature=0`：随机性越高越难收敛，修错要"确定性"
2. 必须把**模型的错误输出 + 错误原因**一起回灌，否则它会重复同样的错

## 任务 5｜成本核算

**5.1** mock 8 条 = **0.006235 元**（≈ 0.00078 元/条，因为 mock 的 token 少）。

**5.2 真实场景**

```
单条 = (1500 × 1 + 800 × 2) / 1_000_000 = 0.0031 元
月   = 0.0031 × 500 × 30            = 46.5 元/月
年   = 558 元
```

结论：**技术成本可以忽略，真正的成本是人**。
所以"要不要做"的决策依据不是模型费，而是**省下的人力 / 减少的错误**（回到第 2 章的 ROI）。

**5.3 三个降本措施**

| 措施 | 预计省 | 代价 |
|---|---|---|
| 缓存（同产品不重复生成） | 命中 50% 省 50% | 要设计缓存键；产品改了要失效 |
| 模型分级（简单款用小模型） | 60%–80% | 要判断"简单"；质量可能下滑，要评估集兜住 |
| 批处理（一次请求 5 条） | 30%–50% | 输出结构复杂，单条失败会连累一批 |

**注意**：省 46.5 元/月毫无意义。降本的真正场景是**每天 10 万条**，
或者是**延迟**（晚 30 分钟出报表影响早会），而不是钱。

## 任务 7｜自审参考答案

1. **可程序判定**：长度、条数、禁用词、语言、关键词命中、JSON 结构。
   **必须人工**：卖点是否真、是否好读、是否符合品牌调性、有没有夸大。
2. 用数据回应："本轮评估集 20 条，通过率 85%，失败集中在标题超长（12 次）；
   人工抽检 5 条，3 条认为卖点顺序不合理。" —— 比"我觉得还行"强一万倍。
3. **不可校验的要求**（如"要有吸引力"）最危险：它无法验收，改了 prompt 也不知道好坏。
   → 要么翻译成可测的代理指标（含 ≥2 个使用场景词），要么承认它只能人工判。
4. **注入拦截在三层**：输入做分隔与转义 → system prompt 声明"用户内容是数据不是指令" →
   输出校验（禁用词 + 关键词 + 结构）。**只靠 prompt 是拦不住的。**

## 关于测试夹具的一个真实教训

第一次跑测试时挂了：`test_合法输出通过校验` 报 `每条 120-300 字符` 失败。

原因是我写的 `GOOD` 样例五点只有 90 来字符——**夹具本身不合规**，
测试在验证一个错误的"正确样例"。

> 这类问题的价值：**测试的夹具必须自己先过一个"合理性"检查**。
> 更稳的写法是在 `setUpClass` 里断言 `validate_listing(GOOD, p) == []` 之前，
> 先断言 `len(GOOD["bullets"][0]) >= 120`，让失败信息直指夹具而不是被测代码。
