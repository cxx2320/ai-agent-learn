## 任务 1｜注册定时任务

```powershell
schtasks /Create /TN DailyReport /XML .\deploy\task-scheduler.xml /F
schtasks /Run /TN DailyReport
Get-ScheduledTask -TaskName DailyReport | Get-ScheduledTaskInfo
```

**看三个字段**：

| 字段 | 正常 | 异常含义 |
|---|---|---|
| `LastRunTime` | 今天是昨天/刚才 | 还停在几天前 → 触发没生效 |
| `LastTaskResult` | 0 | 非 0 → 跑了但失败 |
| `NextRunTime` | 明天 08:10 | 空 → 任务被禁用 |

**批改要点**：
- 只贴截图不说结果 → 扣分
- 没验证 `LastTaskResult` → 等于没验证
- 加分：主动试了"关机再开机后会不会补跑"

## 任务 2｜四种故障演练

| 故障 | 现象 | 退出码 | 判定 |
|---|---|---|---|
| A 数据源缺失 | `[CRIT] 数据源存在 找不到 …business_report_us.csv` | 2 | 正确 |
| B 产物过期 | `[CRIT] 产物 report.md 已 N 小时未更新` | 2 | 正确 |
| C 产物为空 | `[CRIT] 产物 daily_asin.csv 文件过小（0 字节）` | 2 | 正确 |
| D 数字不对（月度） | `[CRIT] 对账残差 残差 12.50 超过容差 1.00` | 2 | 正确 |

**两个必答题的参考答案**

**Q1：哪种故障现在的检查发现不了？**

至少能说出两类（说出一类即及格）：

1. **数字错了但"看起来合理"**：比如汇率取错（7.12 写成 7.0），销售额差 1.7%，
   对账残差仍可能为 0（因为两边同口径）。健康检查看不出来，**只能靠抽样核对**。
2. **产物是对的，但业务没看**：跑成功了，但没人打开。这需要**使用埋点**（第 8 章）。
3. **数据源换了但字段还在**：比如 `units_ordered` 变成了"含取消单"的口径，
   列名没变、行数没变，检查全绿——**这是最危险的一种**。

> 这题考的是"你能不能想到自己的检查有盲区"。答"都覆盖了"= 不合格。

**Q2：哪一句能让你不动代码就知道该找谁？**

> "数据源存在：找不到 business_report_us.csv" → 找**上游/运营**（报表没下载）
> "产物 report.md 已 30 小时未更新" → 找**自己**（调度问题）
> "对账残差 12.50 超过容差" → 找**财务**（口径分歧）

加分：把这三句直接写进告警文案（`notify.py` 的 detail 里带"建议动作"）。

## 任务 3｜告警文案改造

**参考改写**（四要素齐全）：

```
🚨 日报任务失败（需处理）
任务：daily-report    日期：2026-11-18
时间：2026-11-19 08:30:12
失败项：对账残差 26981.06 超过容差 1.00
影响：今日日报数字不可信，不要直接发早会
建议：① 单日跑请加 --skip-reconcile；② 对账请按月跑
负责人：@小李
```

**为什么"影响什么"最重要**：

> 其他三行告诉你"发生了什么"，只有这一行告诉你"**我现在要不要放下手上的事**"。
> 没有它，收到告警的人第一反应是"又要查"——三次之后他就把通知免打扰了。

**批改要点**：
- 只写"运行失败请查看日志" → 0 分（说了等于没说）
- 写了退出码但没写具体失败项 → 半分
- 满分：有失败项 + 有影响 + 有建议动作 + 有人

## 任务 4｜Runbook

判断标准只有一句：**半夜三点、没参与开发的人，照着做能不能恢复。**

合格的 §1.1 应该长这样：

```
$ Get-ScheduledTask -TaskName DailyReport | Get-ScheduledTaskInfo
LastRunTime        : 2026/11/19 8:10:00
LastTaskResult     : 0
NextRunTime        : 2026/11/20 8:10:00
```

不合格的写法：
- "检查任务是否正常"（没法操作）
- "确认数据源"（怎么确认？）

## 任务 5｜权限与密钥审计

| # | 检查 | 期望结果 |
|---|---|---|
| 1 | `Select-String -Path logs\*.log -Pattern "sk-"` | **无结果** |
| 2 | 全项目搜 `api_key =` | 只出现在 `os.environ.get(...)` 里 |
| 3 | `.gitignore` 含 `.env` | 有 |
| 4 | `RunLevel=LeastPrivilege` | 是 |
| 5 | 日志抽样 100 行 | 无买家姓名/地址/电话 |
| 6 | 输出目录权限 | 只有服务账号可写 |

**第 2 项的常见错误**：

```python
# ❌
API_KEY = "sk-xxxx"
# ✅
API_KEY = os.environ.get("LLM_API_KEY", "")
```

**第 5 项最容易被忽略**：管道日志里如果 print 了整行订单（含地址），
一旦日志被同步到共享盘，就是数据事故。

## 任务 6｜预算 / 熔断 / 降级

**参考实现要点**：

```python
MAX_COST_CNY = 1.0
if total_cost >= MAX_COST_CNY:
    log.error("预算上限触发：已花 %.2f 元，停止", total_cost)
    return 1

if consecutive_failures >= 3:
    log.error("熔断：连续 %d 次失败，停止本次运行", consecutive_failures)
    return 1

try:
    data = real_generate(...)
except Exception:
    data = mock_generate(...)
    degraded = True          # ★ 必须显式标注
```

报告里：

```
⚠️ 本次为降级输出（mock），文案未经模型生成。
```

**批改要点**：
- 降级但不标注 → **最严重**，比直接失败还糟（业务以为拿到了真结果）
- 熔断没有重置逻辑 → 第二天仍然熔断，要人工介入
- 预算只算输入不算输出 → 会低估 3–5 倍

## 任务 7｜回滚

```powershell
git tag v0.3                     # 发布前打标
# ...改坏了...
git checkout v0.3                # 回滚
.\deploy\run_daily.ps1 -Date <出问题那天>
```

**验证标准**：健康检查 exit=0，且**产物数字与回滚前那次一致**。

**时间记录**：目标 < 5 分钟。做不到的话，说明你的"发布"依赖了太多手工步骤。

## 任务 8｜它最可能怎么坏

参考排序（概率 × 影响）：

| # | 坏法 | 概率 | 影响 | 现有防线 |
|---|---|---|---|---|
| 1 | 上游改了报表列名 | 高 | 高 | ✅ schema 校验（缺列即报错） |
| 2 | 上游没出数据（人忘了下载） | 高 | 中 | ✅ 数据新鲜度检查 |
| 3 | 机器重启/关机，任务没补跑 | 中 | 中 | ✅ StartWhenAvailable |
| 4 | 密钥过期/额度用完 | 中 | 高 | 🟡 有告警，但无自动降级 |
| 5 | 磁盘满 | 低 | 高 | ✅ 磁盘检查 |

**加分**：给"没有防线"的那条写出**具体补法**（第 4 条：加额度预检 + 降级到缓存）。
