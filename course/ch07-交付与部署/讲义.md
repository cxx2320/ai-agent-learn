# 第 7 章 · 交付与部署：从"我电脑能跑"到"业务敢用"

> **本章目标**：让一个脚本变成**每天自动跑、坏了有人知道、出事能回滚**的服务。
>
> 判据：**业务方不需要问你"今天有没有跑"，也不需要你每天手动看一眼。**

---

## 7.1 四道门：缺一道就不算上线

| 门 | 没有它的后果 | 本章对应 |
|---|---|---|
| **① 定时** | 每天靠人点，等于没自动化 | Task Scheduler / systemd / cron |
| **② 告警** | 挂了三天没人知道 | 健康检查 + 通知 |
| **③ 权限与密钥** | 一个离职/一次日志泄露就出事 | 最小权限 + 环境变量 |
| **④ 回滚** | 改坏了只能现场救火 | 版本号 + 备份 + 回滚脚本 |

**顺序不能反**：先有 ① 才谈 ②，先有 ② 才敢让业务依赖。

---

## 7.2 部署形态怎么选

| 形态 | 成本 | 运维负担 | 适合 |
|---|---|---|---|
| **本机任务计划** | 0 | 低（但依赖那台机器开着） | 内部小工具、验证期 |
| **云服务器 + systemd/cron** | 低（几十元/月） | 中 | 大多数内部工具 |
| **Docker + 定时** | 低 | 中（镜像更新） | 依赖冲突多、要可复现 |
| **内网平台（Airflow/调度系统）** | 高 | 低（平台管） | 多任务依赖、公司已有 |
| **Serverless（定时函数）** | 极低 | 低 | 轻量、无状态、短时任务 |

**决策顺序**：

```
公司已有调度平台？ → 用平台（别自建）
没有，且只是内部小工具？ → 本机任务计划
要长期稳定跑 + 多任务？ → 云服务器 + Docker
要在内网访问数据库？ → 内网机器（合规优先）
```

> **面试坑**："你会部署吗"——正确答法不是"我会 Docker"，而是
> **"我先看公司有什么基础设施，能复用就不自建"**。

## 7.3 调度：三个必须写进配置的事

### ① 时区

- 服务器默认 **UTC**，业务按**北京时间/站点时区**思考
- 容器里必须显式 `TZ=Asia/Shanghai`
- `OnCalendar=08:10` 是**服务器本地时间**，不是你以为的时间

**实测教训**：站点 PST 与北京时间差 16 小时，如果调度在 UTC 08:10 跑"昨天"，
算出来的可能还是前天的数据。

### ② 错过补跑

`StartWhenAvailable`（Windows）/ `Persistent=true`（systemd）。
机器重启、宕机错过一次，恢复后补跑——这就是第 4 章"幂等"的回报。

### ③ 超时

`ExecutionTimeLimit=PT25M` / `TimeoutStartSec=25min`。
**卡死比失败更糟**：失败会告警，卡死会占着下一次的时间窗。

## 7.4 告警：最大的敌人是假警报

### 本轮实测出来的一个真实假警报

包装脚本第一次演练，输出：

```
管道退出码 = 1
健康检查退出码 = 2
对账残差 26981.06 超过容差 1.00
```

看起来像出大事了。实际原因很朴素：

> **结算单是滚动账本**（入账比下单晚 2 天），只跑"昨天一天"时，
> 分子是 1 天的业务数据，分母里却有前后几天的结算流水，**必然不平**。

这不是 bug，是**用错了检查**。如果不修，每天都会告警一次，两周后所有人都会忽略它——
**告警疲劳比没有告警更危险**。

修法（两处）：

```python
# 管道里：短区间跳过对账
if period_days < 7:
    log.info("区间 %d 天 < 7 天，跳过多账残差校验（滚动账本，短区间必然不平）", period_days)
elif abs(residual) > tolerance:
    code = 1
```

```powershell
# 健康检查里：单日运行显式跳过
--skip-reconcile
```

**月跑仍然校验对账**（实测残差 −0.00、退出码 0）。

### 告警设计的四条规则

| 规则 | 反例 |
|---|---|
| 只有需要人处理才告警 | 每次成功都发"今日日报已完成" |
| 告警内容能不动代码就判断 | "任务失败，请查看日志"（哪个日志？） |
| 分级：ERROR 找人，WARN 进清单 | 全部 ERROR → 没人看 |
| 必须有 dry-run | 调试期天天往群里发测试消息 |

### 告警内容四要素

```
什么时候：2026-11-19 08:30:00
哪个任务：daily-report
什么错：对账残差 26981.06 超过容差 1.00
影响什么：今日日报不可信，需人工核对后再发
```

> 第 4 条"影响什么"最常被漏，也最值钱——它决定**看到告警的人要不要现在起床**。

## 7.5 健康检查 ≠ 监控

| | 健康检查（本章的 ops/healthcheck.py） | 监控（Prometheus/Grafana） |
|---|---|---|
| 粒度 | 一次运行 | 持续指标 |
| 回答 | "今天这次算成功吗" | "系统整体趋势如何" |
| 成本 | 极低（一个脚本） | 中高 |
| 什么时候需要 | **上线第一天** | 有多个服务时 |

**先做健康检查，再谈监控。** 一个人维护的工具，一个脚本 + 一条告警就够。

### 检查项清单（本项目的实现）

```
[OK]   数据新鲜度   最新数据 2026-11-30（共 30 天）
[OK]   产物 daily_asin.csv   687 字节
[OK]   产物 report.md        1242 字节
[OK]   对账残差     残差 0.00 在容差内
[OK]   磁盘空间     剩余 655.2 GB
退出码 = 0
```

五个检查项对应五类真实故障：**数据没到 / 产物没生成 / 产物是空的 / 数字不对 / 磁盘满**。

## 7.6 权限与密钥

| 项 | 做法 | 为什么 |
|---|---|---|
| 密钥 | 环境变量 / `EnvironmentFile`（600 权限） | 不进代码、不进日志、不进仓库 |
| 账号 | 单独建服务账号，只给需要的库/目录 | 出问题能定位，离职好交接 |
| 容器 | 非 root（`USER appuser`） | 逃逸风险 |
| 数据 | 日志脱敏（邮箱/电话/地址） | 合规 |
| 访问 | 内网访问，不暴露公网 | 内部工具不需要公网 |

**自检命令**（每次发布前跑一遍）：

```powershell
Select-String -Path logs\*.log -Pattern "sk-|api[_-]?key"    # 应无结果
```

## 7.7 成本与限流（针对调模型的工具）

| 手段 | 实现 | 触发后行为 |
|---|---|---|
| **预算上限** | 累计成本 > 阈值就停 | 停止调用，发告警 |
| **并发限流** | 信号量/队列，最多 N 并发 | 排队而不是打爆 |
| **熔断** | 连续失败 3 次 → 停 10 分钟 | 避免持续烧钱 |
| **降级** | 模型失败 → 用模板/缓存兜底 | 产物降级但不断供 |

> 一句话：**能自动停下来的系统，才是能交给业务的系统。**

## 7.8 发布与回滚

```
v0.1  →  v0.2  →  v0.3
  │        │        │
  └─ tag ──┴─ tag ──┴─ tag（每个能跑的版本都打 tag）
```

**发布三步**：

1. 备份当前能跑的版本（`cp -r` 或 `git tag`）
2. 新版本**先 --dry-run / 小范围跑**（1 天、1 个站点）
3. 看健康检查 + 抽样核对，再全量

**回滚**：`git checkout <tag>` 或替换回备份目录，**一分钟内能恢复**。

> 没有回滚方案的发布，等于赌博。

## 7.9 运维手册（Runbook）

模板在 `starter/ops/RUNBOOK.md`。必须覆盖这 5 个故障：

| 故障 | 第一反应 | 排查步骤 |
|---|---|---|
| 任务没跑 | 看调度器历史 | 触发条件/账号密码/机器是否开着 |
| 跑了但失败 | 看退出码 | 0/1/2 分别对应什么 |
| 数字不对 | 看对账桥 | 哪一项异常 |
| 数据没到 | 看数据新鲜度 | 上游有没有出报表 |
| 磁盘满 | 清日志/归档 | 保留 30 天够不够 |

**写 runbook 的标准：半夜三点、脑子不清醒的人照着做也能恢复。**
