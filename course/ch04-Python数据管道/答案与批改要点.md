### 故障演练（四个实验的实际退出码）

| 实验 | 操作 | 实际结果 |

## 任务 1｜各函数的关键实现点

### `load_config`

```python
root = Path(path).resolve().parent.parent      # config/ 的上一级
merged = {**DEFAULTS, **raw}                   # 浅合并够用
```

三个易错点：
1. **相对路径要相对项目根解析**，不是相对 cwd（否则换个目录跑就找不到数据）
2. `thresholds` 要做**嵌套合并**，否则只改一个阈值就会把其余丢光
3. `llm_api_key` 用 `field(repr=False)`——否则 `print(cfg)` 就把密钥打进日志了

### `read_csv` / `load_sources`

```python
rows = read_csv(p)
lack = REQUIRED[key] - set(rows[0].keys())
if lack:
    raise ValueError(f"{filename} 缺列：{sorted(lack)}")
```

- **缺列抛异常**（结构错了不该硬跑），**缺文件不抛**（记进 `missing` 继续）
- 这两者的区别就是讲义 4.5 的"关键 vs 非关键"

### `site_date_from_bj`

```python
dt = datetime.strptime(ts[:19], "%Y-%m-%d %H:%M:%S")
return (dt + timedelta(hours=-16)).date().isoformat()
```

注意 `ts[:19]`：真实导出常带毫秒或时区后缀，截断比 `strptime` 崩掉好。

### `build_daily_asin`（本章真正的难点）

参考实现的结构：

```
1) 商品主数据 → parent_of / sku_of / children_of
2) business 打底 → 行集，键 (date, asin)
3) ads  → 先聚合到 (date, asin) → 父体按 children_of 平摊 → 再聚合一次   ★ 坑1、坑2
4) settlement → 用 erp 的 order_id 换出下单日 → 按 (site_date, asin) 聚合   ★ 坑3
5) storage → 月度，只挂 posted_date 那一天
6) 组装，net_revenue = sales − refund − commission − fba − ad − storage
```

**三个坑的表现形式**：

| 坑 | 错误实现的结果 | 正确结果 |
|---|---|---|
| 广告不先聚合 | 宽表 210 行（BBB1 有 60 行） | 180 行 |
| 父体广告不平摊 | `Σad_spend = 1058.16` | `2362.54` |
| 费用按入账日归集 | 跨月订单的费用丢失，残差 ≠ 0 | 残差 0.00 |

### `compute_kpis`

```python
"acos": round(ad_spend / ad_sales, 4) if ad_sales else None
```

**分母为 0 返回 None**（报表渲染成 `—`），不要抛异常——一条脏数据不该让整份日报挂掉。

### `reconcile`

```python
refund_timing = refund_biz - refund_posted          # 业务口径多扣的部分
computed = net_sales - commission - fba - ads - storage + refund_timing
residual = settlement_net - computed                # 必须为 0.00
```

`refund_posted` 从结算单里取 `transaction_type == 'Refund'` 的合计；
**这两个口径的差就是那 1,144.82**。

### `find_anomalies`

`duplicate_transaction`、`high_refund_rate`、`low_doi`。

### `render_*` 的两个细节

1. **异常清单 CSV 加 BOM**（`"\ufeff" + ...`）。业务方双击用 Excel 打开，
   没有 BOM 的中文列就是乱码。实测前 3 字节应为 `239 187 191`（EF BB BF）。
2. **`report.md` 里不能出现运行时间**——否则幂等永远失败。

## 任务 2｜幂等

两次 md5 完全一致的三个前提（缺一个就会失败）：

1. **产物里不能有时间戳**——时间只写日志
2. **排序必须显式**（`sorted(rows, key=lambda x: (x["date"], x["asin"]))`）
3. **不能依赖 dict 遍历顺序**（Python 3.7+ 保持插入顺序，但数据源顺序变了就炸）
4. 原子写：`os.replace(tmp, final)`，避免半截文件

> 如果你的 md5 不一致，80% 是把 `datetime.now()` 写进了 report.md。

## 任务 3｜四个故障实验

见上面"实测证据"。要点：

- **A 与 B 的区别就是"关键性"**：主表没了 → 什么都不是；辅助表没了 → 少一块但能用
- **退出码不是装饰**：cron/Airflow/告警系统只看退出码，`0` 就当作成功、不再通知
- **B 的残差 = −2,362.54** 是最有说服力的证据：系统自己指出了"少了什么、少了多少"

**批改要点**：
- 只写"不崩"没写退出码 → 扣分
- 把 B 也做成 exit 2 → 过于保守，业务会抱怨"广告报表没下下来就什么都不给"
- 把 A 做成 exit 1 还产出空报表 → 危险：空报表会被当成"昨天没卖货"

## 任务 5｜增量与默认值

| 场景 | 行数 | 销售额 |
|---|---|---|
| `--start 2026-11-01 --end 2026-11-03` | **18**（6×3） | **4,152.31** |
| `--start 2026-11-03 --end 2026-11-01` | — | `EXIT=2`，`参数错误：start 晚于 end` |
| 不传参数（今天 2026-11-19） | **6**（6×1） | **1,190.51**，日期 = 2026-11-18 |

**要点**：
- 行数 = ASIN 数 × 天数，**不是"有订单的天数"**（0 单的日子也要有行，否则日均会算错）
- 默认"昨天"而不是"今天"——今天的报表还没出完
- 倒序参数应当**直接报错**，而不是默默返回空

## 任务 6｜自审：参考实现也不完美

我把 `solution/` 的毛病列出来，你可以拿它练"挑刺"：

| 坏味道 | 在 solution 里的表现 | 怎么改 |
|---|---|---|
| float 存金额 | `sales_usd` 用 float 累加 | 生产用整数分（`int(round(x*100))`）或 `Decimal` |
| 无 run_id | 日志里无法区分两次运行 | 生成 `run_id` 只进日志/异常清单 |
| 单站点硬编码 | 只有 US 站，`sites` 配置项没用上 | 把站点维度加进键 `(site, date, asin)` |
| `find_anomalies` 语义混 | `duplicate_transaction` 记 ERROR，但已自动去重 | 已处理的问题应是 WARN，未处理的才 ERROR |
| 无覆盖率 | 不知道哪些分支没测到 | `coverage run -m unittest` |
| 报表格式未统一 | markdown 里 4 位小数 | 统一 `_money()` |

> **这一题的目的不是让你写出完美代码，是让你养成"能看出自己代码哪里会出事"的习惯。**

## 我会怎么追问你

1. "你说关键源缺失就 return 2，那如果 business 文件存在但是空的呢？"（→ 行数校验要兜住）
2. "残差 0.00 你就敢发？如果某天所有数据都是 0，残差也是 0。"（→ 残差是必要条件，不是充分条件，还要看规模校验）
