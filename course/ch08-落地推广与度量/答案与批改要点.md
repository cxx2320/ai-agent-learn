## 任务 1｜读懂示例数据

**1.1 三个回答的参考**

1. **人均 10.5 次说明不了好用**。它可能是一个重度用户撑起来的。
   要看**分布**：4 个人里如果有人只用了 1 次，那才是有问题的信号。
   （用 `weekly_active` 看：W46 有 4 人，W47/W48 只剩 3 人 → 有人流失了）
2. **失败的 3 次原因**（示例数据里是随机的，你的实际输出可能是）：
   `数据源缺失 / 对账残差超容差 / 登录态失效 / 报表字段变更`。
   判断标准：**这类错能否自动恢复**？
   - 数据源缺失 → 不能，要上游补数据 → 该告警
   - 字段变更 → 不能，要改代码 → 该告警 + 版本记录
   - 登录态失效 → 能，重试即可 → 该自动重试，不该告警
3. **周活 4 → 3 → 3**：第 2 周流失 1 人，第 3 周没再流失。
   这是"初步被接受但没扩散"的状态——**下一步是搞清楚那 1 人为啥不用**。

**1.2 留存**

```python
weekly = mt.weekly_active(events)
weeks = sorted(weekly)
rate = mt.retention(events, weeks[0], weeks[-1])   # 首周到末周
```

- 留存 < 30% → **先别加功能**，去找流失的人聊（大概率是"数据不信"或"多了一步"）
- 留存 > 70% → 说明进入工作流，可以开始推第二个场景

> 注意：只看"总次数"永远发现不了流失。**存量掩盖流失**是数据汇报最常见的陷阱。

## 任务 2｜埋点方案

| 事件 | 何时触发 | 关键字段 | 回答什么 |
|---|---|---|---|
| `run` | 管道每次执行 | duration_s / ok / error | 工具跑得怎麼樣 |
| `view_report` | 用户打开日报 | user / ts / channel(群/链接) | 有没有人看 |
| `ack_anomaly` | 用户点"已确认/已处理" | anomaly_type / user | 异常有没有被处理 |
| `manual_override` | 用户手工改工具结论 | field / before / after / user | 工具哪里不可信 |

**三个必答**

1. **最能说明"真被用起来"的是 `ack_anomaly`**。
   `run` 只证明程序在跑（可能是定时任务自动跑的，没人看）；
   `ack` 证明**有人做了决策**。
2. **只埋 `run` 会漏掉"有人看吗"**。结果就是"工具很成功，42 次运行"，
   但一问"谁在用"你答不上来。
3. **去重**：按 `event_id` 去重（`append_jsonl` 已实现），
   并保证上报失败可重试（幂等）。

**加分**：`manual_override` 是最值钱的事件——它说明人还在改工具的结论，
**每一行 override 都是一个改进线索**。

## 任务 4｜基线取证

**4.1 三天取证方案**

```
对象：小李（实际操作者）
时间：连续 3 个工作日
记录：开始时间（登录后台那一刻）、结束时间（发到群里那一刻）、
      中间被打断的时长（接电话/开会要扣掉）
工具：让她自己在纸上记，你每天下班前收一次
```

**4.2 可信度对比**

| 方式 | 可信度 | 成本 | 什么时候用 |
|---|---|---|---|
| 工时记录 | 高 | 中（打扰用户 3 天） | 要写进汇报、要算钱 |
| 抽样计时 | 中 | 低（你坐旁边 5 次） | 快速估算 |
| 访谈估算 | 低 | 极低 | 立项阶段粗算 |

**4.3 基线变 55 分钟后的重算**

```
节省工时 = 42 × (55 − 6) / 60 ≈ 34.3 小时
折合金额 = 34.3 × 90 ≈ 3,087 元
```

对比原来（90 分钟基线）：62.9 小时 / 5,664 元。

> **结论：基线从 90 分钟降到 55 分钟，收益缩水 45%。**
> 这就是为什么"我觉得要一个多小时"这句话，在汇报里是**危险的**——
> 它可能让你的结论打对折。

## 任务 6｜诊断"工具没人用"（本章核心）

### 6.1 分类表

| 现象 | 问题类型 | 依据 |
|---|---|---|
| 4 人只有 2 人用 | **推广/认知** | 主管都不知道，说明没人传播 |
| 第 2 周只剩 1 次 | **信任/体验** | 用过一次就不用了，通常是结果不可信或多一步 |
| "怕否错，还是自己看" | **信任** | 工具没有置信度标注，用户不敢依赖 |
| "不知道有这东西" | **认知** | 上线没有公告/培训 |
| "报表字段变更" | **质量/稳定性** | 上游变更导致失败，且没有 schema 预警 |

### 6.2 本周三个动作（按性价比排序）

1. **找老王聊 20 分钟**（成本最低、信息量最大）
   问："清单里哪几条你觉得不该否？为什么？"→ 拿到规则偏差的具体案例。
   预期：能立刻改进 1–2 条规则，并让老王产生参与感。
2. **给清单加置信度与依据**（半天）
   每条后面标"依据：花费 120 美元 / 0 单 / 点击 218"，并区分"建议否定 / 建议观察"。
   预期：解决"怕否错"，这是他不用的**直接原因**。
3. **群公告 + 15 分钟演示**（1 小时）
   把主管拉进来，明确谁负责看。
   预期：利用率从 2/4 提到 4/4。

### 6.3 结论

**改造，不是止损。**

理由：价值是真实的（老王承认"清单跟我看的差不多"，说明准确率不低），
问题全部在**信任与推广**，而这两个都是低成本可修的。
止损的信号（留存长期低 + 失败原因不可修 + 维护成本高于收益）一个都不成立。

**但有一个前提条件**：如果两周后留存仍低于 30%，就止损。

## 任务 7｜止损三判断

| 场景 | 结论 | 理由 | 前提条件 |
|---|---|---|---|
| A 留存 8% 但每次都有真发现 | **改造** | 价值真实存在，只是没进流程 | 找到"为什么不用"的具体原因 |
| B 留存 75% 但成功率 62%、每周修 2 次 | **改造（优先修质量）** | 有人用说明价值成立，质量是主要矛盾 | 一个月内成功率提到 90%，否则止损 |
| C 留存 40%，维护 4 小时/周换来省 3 小时 | **止损** | 净负收益，且维护成本是你自己的时间 | 除非能降到 1 小时/周以内 |

**评分要点**：
- 只给结论不给前提 → 扣分（真实决策都是有条件的）
- 场景 C 答"继续做" → 不合格（这是典型的沉没成本陷阱）

## 任务 8｜自审参考答案

1. **留存多少？** 如果你答不出数字，说明你没埋点——那"工具很成功"就是感觉。
2. **基线怎么来的？** 答"用户说的大概" → 你的 ROI 站不住。
3. **30 秒能答吗？** 练到能脱口而出："3 周 42 次，省 34 小时，成本 5 分钱，
   风险是 1 人流失。"
4. **停掉谁会来找你？** 如果没人来，说明它还没进入任何人的工作流——
   **这是最诚实也最该警惕的自测**。
