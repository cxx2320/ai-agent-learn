# 第 8 章 · 落地推广与效果度量

> **本章目标**：让工具**真的被用起来**，并用数据证明它有价值。
>
> JD 第四条职责原话："推动工具在业务团队中实际使用……跟踪效率、结果质量、使用成本及业务效果"。
> 这一章考的不是技术，是**影响力**。

---

## 8.1 工具做出来了，为什么没人用

真实原因排名（不是猜的，是普遍经验）：

| # | 原因 | 典型表现 | 解法 |
|---|---|---|---|
| 1 | **数字对不上** | "跟我后台不一样，我不敢用" | 第 3 章的口径与对账 |
| 2 | **多了一步操作** | 还要登录、还要填参数、还要另存 | 减少一步，胜过加十个功能 |
| 3 | **不知道有这东西** | 只有你和主管知道 | 群公告 + 15 分钟演示 |
| 4 | **出过错，不再信任** | 一次错数，永久弃用 | 人审环节 + 显式标注置信度 |
| 5 | **不做也没事** | 没有考核、没有 deadline | 找一个"非用不可"的场景切入 |

> **最重要的一条**：前两条加起来占八成。
> 所以"没人用"通常不是功能不够，而是**数据不可信**或**用起来麻烦**。

## 8.2 推广五步（按顺序做，别跳）

### 第一步：找一个种子用户

- **不要找最忙的人，也不要找最反对的人**
- 找那个"现在正在受苦、且愿意跟你聊 20 分钟"的人
- 让他参与设计（第 2 章的访谈），他会成为你的**内部推销员**

### 第二步：并行验证一周

让种子用户**手工和工具同时做**，每天对比一次。

目的不是"证明工具对"，而是**发现你没想到的差异**：
时区、退款口径、某个站点的报表格式不一样……

> 并行的这一周，是你唯一能低成本发现"信任问题"的窗口。

### 第三步：15 分钟培训（不是 1 小时）

只讲三件事：
1. 什么时候用（每天早上 9 点前）
2. 三步操作（打开 → 点一下 → 看结果）
3. 出问题找谁（贴你的企微/飞书）

**不要讲原理、不要讲架构、不要讲模型。** 用户不关心。

### 第四步：做一个"示范案例"

把一次真实发现做成截图：

> "11 月 12 日，工具在早报里标出 B0C1BBB1 库存只剩 3.6 天，
> 当天补货，避免了一次约 3,000 美元的断货。"

一个具体案例的说服力，胜过十张指标图。

### 第五步：写进 SOP

```
运营每日 SOP 第 3 条：
  08:50 打开日报（链接），核对 3 个异常项，异常找小李确认。
```

**只有进了 SOP，工具才算真正落地。** 否则永远是"那个挺好用的小工具"。

## 8.3 埋点：记什么，不记什么

### 记什么（最小集）

| 字段 | 例子 | 用途 |
|---|---|---|
| `event_id` | `E00123` | 去重（重试会重复上报） |
| `ts` | `2026-11-18T09:12:00` | 时间分布、周活 |
| `user` | `li` | 使用人数、留存 |
| `tool` / `action` | `daily-report` / `run` | 区分功能 |
| `ok` | `true/false` | 成功率 |
| `duration_s` | `5.96` | 效率 |
| `cost_cny` | `0.0013` | 成本 |
| `error` | `对账残差超容差` | 失败归因 |

### 不记什么

- 订单明文、买家姓名/地址/邮箱（合规）
- 完整 prompt 与模型输出（体积大，另存样本即可）
- 密码/密钥（永远不进日志）

### 一条铁律

> **埋点必须幂等。** 重试、补跑、断点续传都会重复上报。
> 不去重的话，你的"使用次数"会凭空翻倍，然后你拿着虚高的数据去汇报。

## 8.4 四类指标：缺一类就会被问穿

| 类别 | 指标 | 回答什么问题 |
|---|---|---|
| **使用** | 活跃人数、覆盖天数、人均次数 | 有没有人用 |
| **效率** | 平均耗时、节省工时 | 快了多少 |
| **质量** | 成功率、失败原因分布 | 对不对 |
| **成本** | 单次成本、月成本 | 贵不贵 |

### 最硬的指标：留存

```python
retention(events, cohort_week="2026-W46", later_week="2026-W48")
```

> "第一周用的人，第三周还在用吗？"

**为什么它比总次数重要**：总次数会被 1 个重度用户撑起来；
留存反映的是**是否进入工作流**。留存 < 30% 基本说明失败。

### 本仓库示例数据的真实输出

```
运行次数 42 / 使用人数 4 / 覆盖天数 15 / 成功率 92.86%
单次成本 0.001258 元 / 总成本 0.0528 元
周活：W46=4 → W47=3 → W48=3      ← 有 1 人流失，这就是留存问题
```

**注意最后一行**：总量在涨、但周活在跌，这是"看起来热闹、其实在流失"的典型信号。

## 8.5 前后对比：唯一能拿出的证据

### 三个必须守的规矩

| 规矩 | 反例 |
|---|---|
| **同口径** | 上线前算"含退款"，上线后算"不含退款" |
| **写清基线** | "人工要 90 分钟"——谁说的？怎么测的？ |
| **区分因果与相关** | 同期还上了新广告策略，却把 ACOS 下降全算给工具 |

### 基线怎么取（三个来源，按可信度排序）

1. **工时记录**（最硬）：让用户记 3 天的实际耗时
2. **抽样计时**（次之）：你坐旁边掐表 5 次
3. **访谈估算**（最软）：用户说"大概一个多小时"

> 汇报时**必须写明来源**。写"访谈估算"没人会说你，写不出来才会被质疑。

### 价值换算公式

```
节省工时 = 次数 × (人工单次分钟 − 工具单次分钟) / 60
折合金额 = 节省工时 × 时薪
净收益   = 折合金额 − 工具成本
```

示例数据实测：

```
上线后 42 次，人工基线 90 分钟/次
节省 62.9 小时 ≈ 5,664 元（时薪 90 元）
工具成本 0.05 元
```

**然后立刻补一句**（这句最体现专业度）：

> "以上是**过程指标**。业务结果（少亏的钱、多赚的毛利）需单独取证，不能直接等同。"
>
> 因为"省了 62.9 小时"不等于"多赚了 5,664 元"——时间可能只是让人早下班了。

## 8.6 一页纸汇报模板

```markdown
# <工具名> 上线复盘（第 N 周）

## 一句话
上线 3 周，4 人使用、42 次运行、成功率 92.9%，节省约 63 小时，
成本 0.05 元；当前风险：1 人流失。

## 用了没
| 指标 | 数值 |
（人数 / 次数 / 覆盖天数 / 周活趋势）

## 好不好用
（成功率 / 失败原因 Top3 / 平均耗时）

## 值多少
（节省工时 / 折合金额 / 成本 / 净收益 + 基线来源）

## 下步做什么
（1 个改进 + 1 个推广动作，各带负责人和日期）
```

> **汇报的黄金法则**：先说结论，再说数据；**一定写"风险"**。
> 只报喜的汇报，第二次就没人信了。

## 8.7 迭代节奏

| 频率 | 看什么 | 决定什么 |
|---|---|---|
| 每天 | 有没有跑成功 | 要不要手动补 |
| 每周 | 使用人数、失败原因 Top3 | 本周修哪个 bug |
| 每月 | 留存、ROI、业务结果 | 继续投入还是止损 |

---

## 8.8 什么时候该止损

三个信号，出现两个就该考虑停：

1. **连续 3 周留存 < 30%**
2. **失败原因长期是同一个，且不是你能修的**（比如数据源拿不到）
3. **维护成本 > 它省下的时间**（一个人每周修 3 小时，只为省别人 2 小时）

> 止损不丢人，**硬撑一个没人用的工具才丢人**。
> 而且"我主动下线了一个不达预期的项目"是面试里非常加分的回答。
