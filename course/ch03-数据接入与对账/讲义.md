# 第 3 章 · 数据接入与清洗：口径、多源、对账

> **本章目标**：给你三张来自不同系统、时区不同、口径不同的报表，你能把它们变成**一张可信的宽表**，并能解释**每一分差额从哪来**。
>
> **为什么这章最像真实工作**：JD 第二条职责就是"数据接入、清洗和处理"。跨境公司 90% 的数据在手工下载的 Excel 里，而它们的时区、口径、命名全都不一致。**能不能对上账，决定业务方信不信你的工具。**

---

## 3.1 一个判断，决定你在这行的段位

初级：把数据 join 起来，算出数。
中级：join 之前先问"这一行代表什么"，算完能解释差异。
高级：把口径写成文档，让全公司只有一个数。

> 面试官问"你怎么保证数据准"，正确答案不是"我写了测试"，而是
> **"我先定义口径和粒度，再用三方对账验证，最后出一个残差为 0 的对账桥。"**

---

## 3.2 三个时区：所有跨境数据问题的第一来源

同一笔订单，在三个系统里有三个"日期"：

| 系统 | 用的时间 | 你看到的日期 |
|---|---|---|
| 亚马逊业务报告 | 站点时区（US = PST，UTC−8） | 11-30 |
| 结算报告 | **UTC** | 12-01 |
| ERP / 财务 | 北京时间（UTC+8） | 12-01 |

**关键数字**：PST 与北京差 **16 小时**。所以：
- 站点 11-30 08:00 之后的订单 → 北京时间已经是 12-01
- 站点 11-30 16:00 之后的订单 → UTC 已经是 12-01

### 三条铁律

1. **存储用 UTC 时间戳**，展示时再转成本地时间。
2. **每个表都保留两个日期字段**：`report_date_site`（原样，站点时区）和 `date_utc`（换算后）。对账时明确说用哪个。
3. **永远不要用"本地日期"去 join "站点日期"**——这就是那个经典 bug：
   `WHERE erp.purchase_date = biz.report_date` → 45% 的订单对不上。

### 自检题
> 站点 11-30 的订单，在 ERP 里可能出现在 11-30 或 12-01。那么"11 月总销量"应该以哪个为准？

答案：**以业务报告（站点时区）为准**，因为平台 GMV 就是这么统计的；ERP 的日期只用于内部履约分析，且必须先换算。

## 3.3 口径：同一件事的五种算法

### 销售额的五层

```
① GMV / 下单金额       = Σ 售价 × 件数            （最虚，含未付款、含取消）
② 销售额（业务报告）    = 不含取消、不含税、未扣退款  （平台口径，常用）
③ 净销售额             = ② − 退款
④ 结算净额（回款）      = ProductSales − 佣金 − 配送费 − 退款 − 服务费
⑤ 毛利                = ④ + 未结算调整 − 采购成本 − 头程 − 仓储 − 汇损
```

**报出任何一个数，必须同时说清是第几层。** 说不清，就会吵架。

### 三个高频口径分歧

| 分歧 | 两种算法 | 差多少 |
|---|---|---|
| 退款归哪天 | 下单日（业务报告） vs 退款发生日（结算） | 本数据集差 **1,144.82 美元** |
| 广告销售额 | 归因 7 天 vs 14 天 | 差 5%–15% |
| 佣金 | 配置的类目费率 vs 平台实际扣费 | 本数据集 BBB1 差 **2 个百分点** |

## 3.4 数据分层：ODS → DWD → DWS → ADS

```
ODS  原样落地，一行不改（CSV 原封不动进库）
  ↓  清洗：去重、类型、时区、缺失、单位
DWD  明细层：一行一个业务事实（订单/交易/日×ASIN），口径已统一
  ↓  聚合
DWS  汇总层：日/周/月 × ASIN/站点/类目，指标只在这里定义
  ↓
ADS  应用层：日报、看板、导出 Excel
```

### 唯一原则

> **一个指标只能在一个地方定义一次。**

口径打架的根因 90% 是：日报在 Excel 里算一遍、看板在 SQL 里算一遍、汇报时又手算一遍。
学会把 `ACOS` 的定义写进 DWS 的一处代码 + 数据字典，你就解决了公司一半的数据争议。

## 3.5 粒度：join 之前先问"这一行代表什么"

| 表 | 粒度 | 主键 |
|---|---|---|
| `business_report` | 日 × ASIN | (report_date, asin) |
| `ads_campaign` | 日 × campaign | (report_date, campaign_name) |
| `erp_orders` | 订单行 | order_id（但可能重复抓取） |
| `settlement` | 交易流水 | transaction_id |
| `ads_search_term` | 周 × 关键词 | (week_start, campaign_name, keyword) |

### 最经典的翻车：粒度不一致 + join = 数字放大

```sql
-- 错：业务报告（日×ASIN，1 行）join 结算（订单级，N 行）
SELECT SUM(b.ordered_product_sales_usd) ...
FROM business_report b JOIN settlement s ON b.asin = s.asin;
-- 结果：销售额被放大了 N 倍（N = 该 ASIN 的交易笔数）
```

**症状**：算出来的销售额是后台的 5 倍 / 0.2 倍。
**修法**：先各自聚合到同一粒度，再 join；或明确这是"一对多展开"并知道自己在做什么。

## 3.6 清洗清单（照着过一遍，别靠记性）

| # | 问题 | 危害 | 处理 |
|---|---|---|---|
| 1 | 重复行 | 金额翻倍 | 按**业务主键**去重（`transaction_id`），不是按整行 |
| 2 | 空值 | `AVG` 被拉偏、比率算错 | `COALESCE` / 显式过滤 / 标记 |
| 3 | 0 分母 | 除零报错或 `null` | `NULLIF(x, 0)` |
| 4 | 类型 | 字符串比较 `'9' > '10'` | 入库时定型，或 `CAST` |
| 5 | 币种/汇率 | 人民币美元混算 | 统一到 USD，汇率单独成表 |
| 6 | 逻辑矛盾 | units=0 但 sales>0 | 打标记，进"异常清单"，别硬改 |
| 7 | 取消/退款单 | 虚高 GMV | 按状态过滤，并记录过滤条数 |
| 8 | ID 映射缺失 | 有订单没商品 | 左连接 + 保留未匹配行，输出到异常清单 |
| 9 | 时区 | 日汇总错位 | 见 3.2 |
| 10 | 精度 | 1 分钱对不上 | 金额用整数分，或统一 `ROUND(x,2)` + 容差 |

## 3.7 对账方法论：桥（Bridge）+ 归因树 + 容差

### 对账要回答三个问题

| 维度 | 问题 | 做法 |
|---|---|---|
| **完整性** | 有没有漏？ | 行数/件数比对：`count(distinct order_id)` 三方比 |
| **准确性** | 金额对不对？ | 逐单金额比对，列出差异单 |
| **一致性** | 口径一样吗？ | 对不上时，先用"桥"解释，而不是改数 |

### 桥（Reconciliation Bridge）

```
起点 A（比如业务报告净销售）
  − 项目1（佣金）
  − 项目2（配送费）
  − 项目3（广告+仓储）
  + 项目4（退款时点差）
= 终点 B（结算净额）
残差 = 0  ✅
```

**残差不为 0 说明还有没解释的项目。追到 0 为止——这就是对账。**

### 容差（Tolerance）

不是所有差异都是 bug：

- 金额：`±0.01 × 笔数`（浮点/舍入）
- 比率：`±0.1pp`
- 超出容差 = 真差异，必须归因

## 3.8 本章数据集的桥（先看结构，别记数字）

```
业务报告销售额            46,322.64
− 业务报告退款             2,306.31
= 净销售额                44,016.33
  − 佣金（实际扣费）        7,165.92
  − FBA 配送费             8,999.50
  − 广告费                2,362.54
  − 仓储费                   91.70
  + 退款时点差（结算未入账） 1,144.82
= 结算净额（去重后）       26,541.49  ← 必须与结算单一致，残差 0
```

> 注意最后一项是**加**：业务报告已经扣了 2,306.31 的退款，但结算只扣了 1,161.49
> （因为部分退款在 12 月才入账），所以对账时要**加回** 1,144.82。

**这就是"桥"的精髓：不是把差异抹平，而是逐项解释。**

## 3.9 宽表：把三张表变成一张能用的表

目标表 `dwd_daily_asin`（日 × ASIN），最少包含：

```
date_site, asin, parent_asin, sku, sessions, units_ordered, sales_usd,
refund_usd, ad_spend_usd, ad_sales_usd, commission_usd, fba_fee_usd,
storage_fee_usd, net_revenue_usd
```

**构建顺序（重要）**：

1. 业务报告 → 打底（它决定行集：**每个 日×ASIN 必须有行，哪怕全是 0**）
2. 广告报表 → 左连接聚合到 日×ASIN（品牌广告挂在父体上，需要映射）
3. 结算单 → **先聚合到 日×ASIN**，再左连接（绝不直接 join 明细）
4. 库存快照 → 只挂月末值（不要按日 join）

**为什么"打底"是业务报告**：宽表要回答"卖了什么"，不是"收了多少钱"。
行集选错，后面所有指标都会缺行或多行。

## 3.10 交付物：数据字典与口径文档

一个合格的交付不是一个 CSV，而是**三件套**：

1. **数据字典**：表名、字段、类型、单位、来源、更新频率、负责人
2. **口径文档**：每个指标的定义 + 公式 + 边界（含不含退款/税/运费）
3. **已知问题清单**：哪些数据是脏的、已知偏差多大、怎么规避

模板：

| 字段 | 中文 | 类型 | 单位 | 口径定义 | 来源 | 已知问题 |
|---|---|---|---|---|---|---|
| `ordered_product_sales_usd` | 商品销售额 | decimal | USD | 不含税、不含运费、未扣退款、不含取消单 | 业务报告 | 黑五促销价为成交价 |

## 3.11 十个必踩的坑

1. 粒度不一致就 join → 数字放大
2. 用浮点比较金额 → `0.1+0.2 != 0.3`
3. 忘了过滤取消单
4. 用北京时间 join 站点日期
5. 0 分母没处理 → `CVR = inf`
6. `AVG` 被 NULL 静默跳过
7. SKU ↔ ASIN 一对多，join 后行数暴涨
8. 汇率取哪天没说清（月初/月末/日汇率，差 0.5% 就是钱）
9. 去重按整行去重，漏掉"金额相同但业务上重复"的单
10. 没设容差 → 追 1 分钱追一整天
