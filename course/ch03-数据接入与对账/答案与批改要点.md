## 任务 2｜时区换算

**2.1**
```sql
date(purchase_date_bj, '-16 hours')   -- 北京时间 → UTC(-8h) → 站点时区 PST(-8h)
```

**2.2 / 2.3 关键结论：**

| 状态 | 结果 |
|---|---|
| **不换算** | 31 天全部对不上：11-01 ERP 17 vs 报告 63（**−46**）；12-01 ERP 71 vs 报告 0（**+71**） |
| **换算后** | **31 天全部为 0 差异**，合计 1964 = 1964 |

**三个问题的答案：**

1. **11-30 vs 12-01**：不换算时 ERP 把 11-30 晚上（站点时间）的 71 单记到了 12-01，导致 12-01 凭空多出 71 单、11-01 又少了 46 单。
2. **换算后月底还有差异吗**：没有。换算后每天误差都为 0，说明 **ERP 没丢单，问题纯粹是时区**。
3. **11-01 为什么是负的**：数据集从 11-01 开始，10-31 的订单不在里面，所以月初天然偏低——这是**数据边界问题**，不是 bug。真实场景里做月度对比必须取"完整月份 + 边界对齐"。

**2.4 结论**：
> "11 月总销量"以**业务报告（站点时区）**为准。因为平台 GMV/销量就是这么统计的，对外汇报、与平台结算都以它为锚。ERP 的日期只能用于内部履约分析，且必须先 `-16h` 换算。

**批改要点**：
- 只写"用业务报告"不写"为什么" → 扣分
- 没发现"不换算时总差为 0 但每天全错" → 这是本题的核心洞察：**总数对了不代表数据对了**

## 任务 4｜对账桥（本章核心）

### 4.1 基础数字

```
业务报告销售额              46,322.64
业务报告退款                 2,306.31
净销售额                    44,016.33
结算净额（去重后）           26,541.49
  ProductSales             46,322.64
  Commission               −7,165.92
  FBAFulfillmentFee        −8,999.50
  Refund                   −1,161.49
  ServiceFee               −2,454.24
```

### 4.2 完整对账桥

```
业务报告销售额                      46,322.64
− 业务报告退款                       2,306.31
= 净销售额                          44,016.33
  − 佣金（实际扣费）                 7,165.92
  − FBA 配送费                       8,999.50
  − 广告费                           2,362.54
  − 仓储费                              91.70
  + 退款时点差（结算未入账）          1,144.82
= 结算净额                          26,541.49   ✅
残差                                    0.00
```

### 4.3 为什么退款时点差是"加"

- 业务报告已扣退款 **2,306.31**（按**下单日**归集）
- 结算里只扣了 **1,161.49**（按**退款发生日**入账，部分退款在 12 月才入账）
- 所以业务口径比结算口径**多扣了 1,144.82** → 对账时必须**加回来**

> **对账桥的本质：把两套口径之间的差，逐项解释清楚，而不是抹平。**

### 4.4 ServiceFee 拆解与跨月

```
ServiceFee 合计 2,454.24
  = 广告费 2,362.54
  + 月度仓储费 91.70   （21.40+13.80+4.90+26.10+17.30+8.20）
```

广告费月度口径差 **124.75** 的原因：
- 广告报表按**站点时区**切日（11-30 的广告费算 11 月）
- 结算按 **UTC** 落账（11-30 的广告费 posted 到 **12-01**）
- 所以"11 月结算单里的广告费"= 2,237.79，比广告报表少 **124.75**（正好是 11-30 当天的花费）

**结论**：月度对账必须**先统一按业务日期归集**，否则每月都差这最后一天。

### 批改要点

| 情况 | 判定 |
|---|---|
| 残差不为 0 却说"基本对上了" | ❌ 这章不及格 |
| 用"调整项"一笔抹平差异 | ❌ 这不是对账，是做假账 |
| 没写"退款时点差" | ❌ 缺了本题唯一的加项 |
| 把 124.75 当成错误，而不是时区归属 | 🟡 结论对，理解错 |

## 任务 6｜宽表

### 关键设计决策（评分看这四点）

1. **打底用业务报告**，保证 6 ASIN × 30 天 = **180 行**（0 单的日子也要有行）
2. **广告先聚合再连接**，否则一个 ASIN 一天多条 campaign 会放大行数
3. **父体广告（SB-Brand-ORG 挂 B0C1PARB）要分摊到子体**，否则这部分花费凭空消失
4. **订单级费用必须归到"下单日"，不能归到"入账日"**
   （佣金/配送费 posted 在下单后 2 天，直接按 posted_date 连接会错位到错误的日期，甚至跨月丢失）

### 参考 SQL

```sql
DROP TABLE IF EXISTS dwd_daily_asin;
CREATE TABLE dwd_daily_asin AS
WITH biz AS (
    SELECT report_date AS date_site, asin,
           CAST(sessions AS INTEGER)            AS sessions,
           CAST(units_ordered AS INTEGER)       AS units_ordered,
           CAST(ordered_product_sales_usd AS REAL) AS sales_usd,
           CAST(refund_amount_usd AS REAL)      AS refund_usd,
           buy_box_pct
    FROM business_report
),
prod AS (SELECT asin, parent_asin, COALESCE(sku,'') AS sku FROM products),
-- 广告：父体花费按子体个数平摊（真实项目应按销量占比加权）
ads_raw AS (
    SELECT report_date AS date_site, asin,
           SUM(CAST(spend_usd AS REAL)) AS sp,
           SUM(CAST(ad_sales_usd AS REAL)) AS sa
    FROM ads_campaign GROUP BY 1,2
),
ads AS (
    -- 父体广告展开到子体：先按子体个数平摊，再聚合回「日 × 子体」，
    -- 否则同一个子体会同时拿到"自己的广告行"和"父体分摊行"，行数翻倍
    SELECT date_site, asin,
           SUM(ad_spend_usd) AS ad_spend_usd,
           SUM(ad_sales_usd) AS ad_sales_usd
    FROM (
        SELECT a.date_site,
               CASE WHEN p.asin IS NULL THEN c.asin ELSE a.asin END AS asin,
               a.sp / CASE WHEN p.asin IS NULL
                           THEN (SELECT COUNT(*) FROM products x WHERE x.parent_asin = a.asin)
                           ELSE 1 END AS ad_spend_usd,
               a.sa / CASE WHEN p.asin IS NULL
                           THEN (SELECT COUNT(*) FROM products x WHERE x.parent_asin = a.asin)
                           ELSE 1 END AS ad_sales_usd
        FROM ads_raw a
        LEFT JOIN products p ON p.asin = a.asin
        LEFT JOIN products c ON c.parent_asin = a.asin
    )
    GROUP BY 1, 2
),
-- 订单级费用：回到「下单日」
order_fee AS (
    SELECT e.site_date, e.asin,
           SUM(CASE WHEN s.transaction_type='Commission'        THEN -CAST(s.amount_usd AS REAL) ELSE 0 END) AS commission_usd,
           SUM(CASE WHEN s.transaction_type='FBAFulfillmentFee'  THEN -CAST(s.amount_usd AS REAL) ELSE 0 END) AS fba_fee_usd
    FROM (SELECT DISTINCT order_id, asin, date(purchase_date_bj,'-16 hours') AS site_date
            FROM erp_orders WHERE status <> 'cancelled') e
    JOIN (SELECT * FROM settlement GROUP BY transaction_id) s ON e.order_id = s.order_id
    WHERE s.transaction_type IN ('Commission','FBAFulfillmentFee')
    GROUP BY 1,2
),
-- 仓储费：月度一次性，只挂到 11-30
storage AS (
    SELECT asin, SUM(-CAST(amount_usd AS REAL)) AS storage_usd
    FROM (SELECT * FROM settlement GROUP BY transaction_id)
    WHERE transaction_type='ServiceFee' AND description LIKE '%Storage%'
    GROUP BY 1
)
SELECT b.date_site, b.asin, p.parent_asin, p.sku,
       b.sessions, b.units_ordered, b.sales_usd, b.refund_usd,
       COALESCE(a.ad_spend_usd,0) AS ad_spend_usd,
       COALESCE(a.ad_sales_usd,0) AS ad_sales_usd,
       COALESCE(ROUND(f.commission_usd,2),0) AS commission_usd,
       COALESCE(ROUND(f.fba_fee_usd,2),0) AS fba_fee_usd,
       CASE WHEN b.date_site='2026-11-30' THEN COALESCE(ROUND(s.storage_usd,2),0) ELSE 0 END AS storage_fee_usd,
       -- 不在行内 ROUND：分摊值带小数，逐行四舍五入会累积误差（180 行能差 0.07）
       b.sales_usd - b.refund_usd
             - COALESCE(f.commission_usd,0) - COALESCE(f.fba_fee_usd,0)
             - COALESCE(a.ad_spend_usd,0)
             - CASE WHEN b.date_site='2026-11-30' THEN COALESCE(s.storage_usd,0) ELSE 0 END AS net_revenue_usd,
       CASE WHEN b.sessions = 0 THEN 'sessions_zero'
            WHEN b.buy_box_pct IS NULL OR TRIM(b.buy_box_pct)='' THEN 'missing_buybox'
            ELSE '' END AS data_flags
FROM biz b
LEFT JOIN prod    p ON p.asin = b.asin
LEFT JOIN ads     a ON a.asin = b.asin AND a.date_site = b.date_site
LEFT JOIN order_fee f ON f.asin = b.asin AND f.site_date = b.date_site
LEFT JOIN storage s ON s.asin = b.asin;
```

### 验证（以下数字是我实测过的，你的实现应当一致）

```sql
SELECT COUNT(*) FROM dwd_daily_asin;                        -- 180
SELECT ROUND(SUM(sales_usd),2)     FROM dwd_daily_asin;     -- 46322.64
SELECT ROUND(SUM(ad_spend_usd),2)  FROM dwd_daily_asin;     -- 2362.54
SELECT ROUND(SUM(commission_usd),2)FROM dwd_daily_asin;     -- 7165.92
SELECT ROUND(SUM(fba_fee_usd),2)   FROM dwd_daily_asin;     -- 8999.50
SELECT ROUND(SUM(storage_fee_usd),2) FROM dwd_daily_asin;   -- 91.70
SELECT ROUND(SUM(net_revenue_usd),2) FROM dwd_daily_asin;   -- 25396.67
SELECT asin, COUNT(*) FROM dwd_daily_asin GROUP BY asin;    -- 每个 30 行
```

**最后一步的闭环验证（这道题真正要你发现的）：**

```
宽表净收入           25,396.67
+ 退款时点差          1,144.82
= 结算净额           26,541.49   ✅
```

> 宽表是**业务口径**（退款按下单日），结算单是**现金流口径**（退款按发生日），
> 两者差的正正好好就是那 1,144.82 —— 这不是巧合，是交叉验证。
> 如果你的宽表算出来是 26,541.49，说明你把退款口径搞混了。

**关于 0.07 的类型误差**：如果你在行内做了 `ROUND(...,2)`，180 行累加会出现 0.0x 的偏差。
这正好验证了讲义"坑 #10"：**分摊 + 逐行四舍五入 = 累计误差，要么保精度，要么设容差（±0.01×行数）**。

## 任务 8｜数据字典（参考片段）

| 字段 | 中文 | 类型 | 单位 | 口径定义 | 来源 |
|---|---|---|---|---|---|
| `date_site` | 业务日期 | date | — | 站点时区（PST），**非**北京/UTC | business_report |
| `sales_usd` | 商品销售额 | decimal | USD | 不含税、不含运费、**未扣退款**、不含取消单 | business_report |
| `refund_usd` | 退款金额 | decimal | USD | 按**下单日**归集 | business_report |
| `ad_spend_usd` | 广告花费 | decimal | USD | 按**站点时区日历日**归集，父体花费已平摊到子体 | ads_campaign |
| `commission_usd` | 平台佣金 | decimal | USD | 平台**实际扣费**，非配置费率计算值 | settlement |
| `storage_fee_usd` | 仓储费 | decimal | USD | 月度一次性，仅挂在月末日 | settlement |

**口径说明三条**：
1. 销售额：不含退款、不含税、不含买家付运费；净额 = `sales_usd − refund_usd`
2. 广告费：按站点时区的广告报表日期归集；与结算单的 UTC 入账日相差 1 天
3. 退款：宽表内按**下单日**归集（与业务报告一致）；结算现金流按退款发生日

**已知问题三条**：
1. 结算存在重复 `transaction_id`（本月 2 笔），汇总前必须去重
2. ERP 时区为北京时间，与站点日期差 16 小时，需 `-16h` 换算
3. `sessions=0` 的异常行会导致 CVR 分母为 0，已标记 `sessions_zero`

## 任务 9｜加分题

**9.1 为什么 `Σ ad_sales` ≠ 业务销售额**

三个原因（答对两个及格）：
1. **归因 ≠ 实际**：广告销售额是"点击后 7/14 天内成交"的归因结果，会回溯变化
2. **重复归因**：同一笔订单可能被多个 campaign/广告组同时计入
3. **范围不同**：自然订单（本数据集约 82%）根本不在广告报表里；反过来品牌广告可能归因到未投放的 ASIN

**9.2 高花费零转化清单**

```sql
SELECT keyword, match_type, week_start, ROUND(CAST(spend_usd AS REAL),2) AS spend
FROM ads_search_term
WHERE CAST(spend_usd AS REAL) >= 80 AND CAST(ad_orders AS INTEGER) = 0
ORDER BY spend DESC;
```

| 关键词 | 匹配 | 花费 | 建议动作 |
|---|---|---|---|
| wireless charger | broad | 120.00 | 加否定 + 降竞价 30% |
| charging cable organizer | broad | 110.00 | 加否定（品类不符） |
| phone stand cheap | broad | 95.00 | 加否定（价格意图不符） |

**9.3 campaign 诊断**

| SP-Manual-WR | 30.89% | 7.42% |
