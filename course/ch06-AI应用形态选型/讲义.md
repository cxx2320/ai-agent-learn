# 第 6 章 · AI 应用形态选型：规则 / RAG / Agent / 浏览器自动化

> **本章目标**：拿到一个业务需求，**30 秒内判断该用哪种形态**，并说清为什么不用另外三种。
>
> 这是这个岗位最容易拉开差距的地方。会用 API 的人很多，**知道什么时候不该用模型**的人很少。

---

## 6.1 五种形态，成本从低到高

| 形态 | 本质 | 成本 | 确定性 | 典型场景 |
|---|---|---|---|---|
| **① 规则 / SQL 脚本** | if-else + 阈值 | 极低 | 100% | 断货预警、对账、日报 |
| **② Prompt 调用**（单次） | 文本进 → 文本出 | 低 | 中 | 翻译、改写、摘要、分类 |
| **③ RAG** | 检索 + 生成 | 中 | 中（可引用） | 政策问答、客服知识库 |
| **④ Agent** | 模型 + 工具 + 循环 | 高 | 低 | 多步任务（查→比→写） |
| **⑤ 浏览器自动化** | 模拟人操作页面 | 高（维护） | 高（但有波动） | 没有 API 的后台下载 |

还有第六种：**微调**。绝大多数公司**用不上**——数据不够、迭代太慢、RAG 能解决 90% 的"知识"需求。

---

## 6.2 决策树：四个问题定形态

```
问题 1：这件事的规则能写下来吗？
  能，且不需要理解自然语言 → ① 规则脚本，直接结束
  ↓ 需要理解文本/图片

问题 2：答案是"知识"还是"动作"？
  知识（政策怎么规定、术语什么意思） → ③ RAG
  动作（下载报表、改价、发邮件） → 问题 3

问题 3：一次能不能做完？
  一次（调一个接口） → ④ 简单工具调用
  多步（先查再比再写） → ④ Agent

问题 4：目标系统有 API 吗？
  有 → 调 API
  没有，只能点页面 → ⑤ 浏览器自动化
```

**口诀**：

> **规则能解决的，绝不上模型；一次能解决的，绝不上 Agent；有 API 的，绝不点页面。**

---

## 6.3 反例：三种"不该用 AI"的典型翻车

| 场景 | 有人会做 | 正确做法 | 为什么 |
|---|---|---|---|
| 判断库存是否低于安全线 | 用模型"分析" | `if available < avg*7: 预警` | 规则 100% 准，模型会算错数 |
| 从订单表查昨天的销售额 | 让模型写 SQL 执行 | 直接 SQL | 一次错就是错数，且无法审计 |
| 每天下载 8 个站点报表 | 让 Agent 点页面 | 平台报表 API / 批量下载 | 页面改版就全崩 |

**判断标准只有一条**：**这件事需要"理解自然语言"吗？**
不需要 → 用确定性代码。需要 → 再考虑模型。

## 6.4 RAG 的真相：检索质量决定 70% 的效果

很多人以为 RAG 的难点是"接一个大模型"，其实难点在这四件事：

| 环节 | 做错的后果 | 占比 |
|---|---|---|
| **切分（chunking）** | 答案被切成两半，检索到前半段 | 30% |
| **召回（recall）** | 该找到的没找到 → 模型开始编 | 30% |
| **重排（rerank）** | 文档对了、章节错了 → 答偏 | 15% |
| **引用与拒答** | 无法核对 / 不知道就说不知道 | 25% |

### 本项目里能验证的三件事

**① 中文必须特殊处理**
中文没有空格，按英文分词会把"月度仓储费"整段当一个 token，永远匹配不上。
本实现用**双字切分**：`月度仓储费 → 月度/度仓/仓储/储费`。

**② 拒答阈值（min_score）是必需品**
没有阈值，问"今天天气怎么样"也会返回三个片段，模型就会开始编。
本项目实测：无关问题返回空列表 → 输出"知识库中没有找到相关规定"。

**③ 重排能救命**
初始版本问"月度仓储费怎么算"，排第一的是**"长期仓储费"**——文档对了，章节错了。
加了"小节标题命中加权"后，正确答案从第二名升到第一名（0.3381 → 0.5096）。

> **这就是 RAG 的真实调试过程**：不是换个更大的模型，而是修检索。

## 6.5 Agent：能力和风险一起放大

### ReAct 循环

```
思考（Thought）→ 选工具（Action）→ 看结果（Observation）→ 再思考 → ... → 回答
```

### 工具设计三原则

1. **一个工具只做一件事**，参数尽量少（`search_kb(query, k)` 而不是 `do_everything(config)`）
2. **返回结构化结果 + 明确的失败原因**（"没找到"要显式返回，不要返回空字符串）
3. **写操作必须二次确认**（加否定词、改价、发邮件 → 默认只给建议，不做执行）

### 四种死法

| 死法 | 表现 | 防法 |
|---|---|---|
| **死循环** | 反复调同一个工具 | 最大步数（如 8 步）+ 重复调用检测 |
| **幻觉调用** | 调不存在的工具/参数 | 工具清单白名单 + JSON schema 校验 |
| **成本爆炸** | 一步一调，20 步烧掉 0.5 元 | 预算上限 + 步骤日志 |
| **错误累积** | 第 2 步查错，后面全错 | 每步记录来源，允许人工中断 |

> **面试金句**：Agent 不是"更聪明的模型"，是"**模型 + 工具 + 循环 + 刹车**"。
> 没有刹车的 Agent 不能上线。

### 本仓库的 Agent 参考实现

在 `starter/agent/`，**不调模型也能跑**（脚本化 planner）：

```bash
cd starter
python -m agent.planner
```

输出：

```
Q: 退货率高会影响利润吗？顺便算 3*29.99
步数: 2  停止原因: None
  [1] search_kb({"q": "退货 利润"}) → ok [amazon-returns.md · 退货率与利润 (0.4669)]
  [2] calc({"expr": "3 * 29.99"}) → ok 89.97
```

三个文件对应三件事：

| 文件 | 职责 | 关键设计 |
|---|---|---|
| `agent/tools.py` | 工具白名单 | 不在表里的名字直接 `unknown_tool`，参数缺失/多余都拒绝 |
| `agent/react.py` | 循环 + 刹车 | `max_steps=8` + 同工具同参数重复 2 次即终止 |
| `agent/planner.py` | 决策层（可替换） | 脚本化；换真实模型只改这一个文件，循环与刹车不动 |

**为什么先做脚本化 planner**：它把"模型决策"和"循环控制"解耦了。
这样循环和刹车可以被 6 个测试覆盖（`tests/test_agent.py`），而不花一分钱。

## 6.6 浏览器自动化：最后的选择

**什么时候必须用**：目标系统**没有 API**，只有网页后台（很多 ERP、部分平台报表）。

**什么时候不要用**：有 API 就用 API（更稳、更快、更合规）。

### 稳定性四件套

1. **显式等待**元素出现，不用 `sleep(3)`
2. **选择器优先级**：`data-testid` > 稳定 id > 文本 > xpath 绝对路径
3. **失败截图 + 页面 HTML 落盘**（否则你永远不知道当时页面长什么样）
4. **登录态复用**（cookie 持久化），但要加密存储，且遵守平台条款

**风险**：页面改版 → 全部失效；平台反爬 → 账号风险。
所以在选型表里，它的优先级排在 API 之后。

### 本仓库的浏览器自动化参考实现

在 `starter/automation/`，**不启动真实浏览器**（用假页面驱动）：

```
automation/driver.py   Page 协议 + FakePage（可模拟超时、记录调用）
automation/task.py     下载编排：重试、单站点隔离、失败截图与 HTML 落盘
```

为什么这么拆：自动化真正难的不是"点页面"，而是**流程编排 + 重试 + 证据留存**。
这三件事和真实浏览器无关，可以用假驱动测；Playwright 只负责实现 `Page` 那几个方法。

真实接入只要写一个 `PlaywrightPage`：

```python
class PlaywrightPage:
    def __init__(self, page):          # playwright.sync_api.Page
        self.page = page
    def goto(self, url):               self.page.goto(url, wait_until="networkidle")
    def wait_for(self, sel, timeout_ms): self.page.wait_for_selector(sel, timeout=timeout_ms)
    def download(self, sel, dest):
        with self.page.expect_download() as d:
            self.page.click(sel)
        d.value.save_as(dest)
    def screenshot(self, path):        self.page.screenshot(path=path, full_page=True)
    def html(self):                    return self.page.content()
```

**换掉驱动，编排代码一行不用改** —— 这就是第 4 章"依赖注入"在这里的用处。

## 6.7 选型矩阵（背下来）

| 需求特征 | 首选 | 备选 | 明确不用 |
|---|---|---|---|
| 规则明确、数据在库里 | SQL/脚本 | — | 模型、Agent |
| 单次文本加工 | Prompt | 微调 | Agent |
| 需要引用原文的知识问答 | RAG | 规则检索 | 微调 |
| 多步、跨系统、要判断 | Agent + 少量工具 | 人工 SOP + 脚本 | 纯 Prompt |
| 目标系统无 API | 浏览器自动化 | 人工下载 | Agent 点页面 |
| 纯计算/对账 | 脚本 | — | 任何模型 |

## 6.8 本章交付的代码

一个**完全离线**的最小 RAG（`starter/`）：

```
corpus/*.md          6 篇平台规则知识库
src/kb/chunk.py      按小节切分 + 超长二次切分
src/kb/retrieve.py   中文双字分词 + TF-IDF + 余弦 + 章节重排 + 拒答阈值
src/kb/answer.py     带引用作答 / 无命中拒答
├─ tests/test_kb.py     9 个离线测试（RAG）
├─ tests/test_agent.py  6 个离线测试（Agent 循环与刹车）
└─ tests/test_automation.py  7 个离线测试（下载编排与稳定性）
```

**实测**：

```
$ python run.py "月度仓储费怎么算"
根据《amazon-fba-fees.md · 月度仓储费》：月度仓储费按商品在运营中心占用的平均体积计费…
引用：amazon-fba-fees.md · 月度仓储费 (0.5096) / 长期仓储费 (0.4524) / 费用构成 (0.1705)

$ python run.py "今天天气怎么样"
知识库中没有找到相关规定。（退出码 3）
```

> 为什么不用向量库：几百个 chunk 的场景，TF-IDF 命中率足够，而且**可解释**
> （你能说清为什么命中）。等知识库上万条、同义改写多的时候，再上 embedding。
